# RTL timing optimisation

Recovering setup slack means removing logic levels between two flops. Nothing
else on this page matters as much as that sentence: a transformation that moves
gates around without shortening the longest path from a launch flop to a
capture flop has not helped, however much better the code looks afterwards.

## The invariants

These are checked by tools after you answer, so there is no benefit in bending
them:

1. **Functional equivalence.** A sequential equivalence check runs against the
   original design. Bit-exact outputs, cycle for cycle. A rewrite that changed
   behaviour is discarded no matter how much slack it recovered.
2. **Latency and interface are fixed.** Same module name, same ports, same
   widths, same pipeline depth. You may redistribute or duplicate registers.
   You may not add or remove a pipeline stage.
3. **Synthesisable Verilog-2005.** No initial blocks, no delays, no testbench
   constructs.

## How to read a critical path

The instance names in an OpenSTA report (`_14637_`, or a long chain like
`acc_out[33]_DFF_X1_Q_D_AOI21_X1_ZN`) are generated by synthesis and carry no
design meaning. The *sequence of cell types* does:

| what you see | what it is |
|---|---|
| a wall of AND/OR feeding a wide reduction | partial-product generation, or a comparison |
| a long run of XOR with AOI/OAI between | carry propagation through an adder |
| repeated MUX cells in series | a priority chain or a select cascade |
| a single stage with fanout in the tens | one net driving a whole datapath |
| delay spread evenly over 80 stages | the depth itself is the problem, not any one cell |

Where the delay sits decides which transformation applies. A path whose delay
is concentrated in five of ninety stages has a local fix; one where it is
spread evenly does not, and needs the structure changed.

## What reliably works

Ordered by how often it recovers real slack:

**Rebalance a serial chain into a tree.** `((a+b)+c)+d` is three adders deep;
`(a+b)+(c+d)` is two. For n terms the depth goes from n-1 to ceil(log2 n), so
the gain grows with every term. This is the single most productive rewrite on
accumulate and reduction logic.

**Move late work off the path.** If a condition is computed *after* a long
arithmetic result and then used to select against it, compute it beside the
arithmetic from the partial results instead. A saturation clamp at the end of a
40-bit accumulate is the textbook case: the overflow condition is decidable
from the operands, not only from the sum.

**Carry-save intermediate sums.** Every full-width add resolves a carry chain.
Keeping a running total as a redundant (sum, carry) pair makes each
intermediate add a constant-depth 3:2 compression and pays for one carry chain
at the very end instead of one per term.

**Replicate a high-fanout driver.** A net driving many loads needs a large
driver or a buffer tree, and both sit on the launching path. Duplicating the
logic that produces it splits the load without changing the value.

**Narrow a comparison to the bits that decide it.** A 40-bit compare against a
constant usually turns on a handful of high bits. So does an equality test
against a sparse constant.

**Retime across existing registers.** Where a pipeline already has stages, work
can be moved between them. The latency must not change -- this redistributes
logic across existing flops, it does not add one.

**Flatten a priority cascade.** A chain of `?:` is a chain of muxes. A one-hot
select decoded in parallel is one mux, and the decode is off the critical path.

## What wastes an iteration

Observed repeatedly, and none of it moves the number:

- Renaming signals, reordering independent statements, adding attributes.
- Restating the same logic with different operators -- synthesis has already
  canonicalised it and will produce the same gates.
- "Optimisations" whose only effect is to move the same gates around.
- Attacking a construct that is not on the critical path. Check the path first;
  an area saving elsewhere does not buy slack here.
- Adding a pipeline stage. It closes timing and fails the check, which is worse
  than not trying, because it also spends an equivalence proof.

## Arguing equivalence

Every rewrite must come with the reason its outputs are bit-identical. Be
specific about two things, because they are where rewrites actually break:

- **Reset.** Does the restructured logic reset to the same values, in the same
  cycle?
- **Width and sign.** Reassociating a sum changes where intermediate values are
  truncated. `(a+b)+c` and `a+(b+c)` are equal in unbounded arithmetic and can
  differ in fixed width if an intermediate overflows. Widen intermediates, or
  say why they cannot overflow.

## Transformation catalogue

Each entry pairs a structural pattern with the transformation that addresses
it. **These carry no evidence yet.** They are textbook suggestions, and the
optimisation loop records how each actually fares -- pass rate on the
equivalence check, and whether it beat its siblings -- so a later run can tell
which of them work on real designs. Until then, treat them as candidates.


### carry propagation across a wide accumulator

**accumulate in carry-save form and resolve with a single carry-propagate adder**

Each full-width add resolves a carry chain. Keeping the running total as a redundant (sum, carry) pair makes every intermediate add a constant-depth 3:2 compression, and only the last step pays for a carry chain.

```verilog
// keep {s, c} redundant through the chain, resolve once at the end
wire [W:0] total = s + c;
```

### deep FSM or decode logic

**pre-decode the next state one cycle early and register the decoded form**

Decoding a binary state register into control signals puts a decoder in series with everything it controls. Registering the decoded (one-hot) form moves the decode off the consuming path without adding latency, because the decode of the *next* state is computable this cycle.

```verilog
// binary state, decoded late
assign en = (state == RUN);
// one-hot, decoded early
always @(posedge clk) en_q <= (next_state == RUN);
```

### high-fanout signal on the critical path

**replicate the driver so each load group has its own copy**

A net driving many loads needs a big driver or a buffer tree; both cost delay on the launching path. Duplicating the logic that produces it splits the load without changing the value.

```verilog
reg sel_a, sel_b;  // two copies of one condition
always @(posedge clk) begin sel_a <= cond; sel_b <= cond; end
```

### long path through an operand shared by many consumers

**isolate the operand per consumer so an idle consumer stops loading it**

Operand isolation removes both switching power and capacitive load from the shared net, shortening the path that drives it.

```verilog
wire [W-1:0] op_for_b = en_b ? shared : {W{1'b0}};
```

### mux-heavy selection logic

**flatten the serial mux chain into a single balanced select**

Nested conditionals synthesise to a chain of 2:1 muxes with depth equal to the nesting. A one-hot or case-based select of the same conditions gives one balanced level of selection instead.

```verilog
// depth 3
assign y = a ? p : b ? q : c ? r : s;
// depth 1 mux tree
always @(*) case (1'b1) a: y=p; b: y=q; c: y=r; default: y=s; endcase
```

### priority encoder or leading-one chain

**reduce with a balanced tree instead of a linear priority scan**

A linear priority chain has depth proportional to width. A tree reduction that combines (found, index) pairs pairwise has logarithmic depth and the same result.


### reset logic in series with the datapath

**move the reset out of the data path and onto the register's own reset**

A reset ANDed into the data expression puts a gate in series with the whole datapath. Using the flop's reset port keeps the datapath clean.

```verilog
// in the path
always @(posedge clk) q <= rst ? 0 : (a + b);
// on the reset port
always @(posedge clk or negedge rst_n)
  if (!rst_n) q <= 0; else q <= a + b;
```

### saturation or clamp after a long arithmetic path

**form the clamp condition beside the arithmetic and apply it as a select, not as a compare-then-select**

A clamp written as compare-then-mux serialises three things: the arithmetic, the comparison, and the selection. The condition usually depends on high bits and overflow flags that the arithmetic produces before its low bits settle.

```verilog
// serial
assign y = (s > MAX) ? MAX : (s < MIN) ? MIN : s;
// condition formed from overflow bits available early
```

### serial accumulate chain

**rebalance the chain into an adder tree**

A left-to-right chain of N adds has depth N-1; a balanced tree has ceil(log2 N). The arithmetic result is identical because integer addition is associative in two's complement of a fixed width.

```verilog
// depth 3
wire [W:0] s = ((a + b) + c) + d;
// depth 2, same value
wire [W:0] s = (a + b) + (c + d);
```

### sign extension replicated before every operand of a wide add

**add the narrow values and sign-extend once at the end**

Sign-extending each product to the accumulator width before adding makes every adder full-width. Adding at the natural width and extending the single result gives the same value with narrower carry chains.

```verilog
// wide adds
wire [39:0] s = {{8{p0[31]}},p0} + {{8{p1[31]}},p1};
// narrow add, one extension
wire [32:0] t = p0 + p1;
```

### unpipelined multiplier array in one cycle

**redistribute the existing registers across the array without changing the latency**

When the module already has registers before and after the multiply, the boundary between them can be moved into the array -- retiming -- so each stage carries less depth. Total latency is unchanged, which is what the equivalence check requires.


### wide comparison at the end of the datapath

**precompute the comparison from partial results in parallel with the final arithmetic**

A compare that waits for the full sum adds its own carry chain on top of the datapath's. The deciding bits are usually available earlier -- the sign and the bits above the limit -- so the condition can be formed beside the sum instead of after it.

```verilog
// serial: sum, then compare
wire over = (sum > LIMIT);
// parallel: the top bits already decide it
wire over = |sum[W-1:LIMIT_BITS] & ~sum[W-1];
```

## Choosing among them

Prefer the transformation that removes the most logic levels from the *measured*
path. When two are comparable, prefer the one whose equivalence argument is
easier to make: a rewrite that cannot be proven equivalent is worth nothing,
and the proof is run on every candidate.
